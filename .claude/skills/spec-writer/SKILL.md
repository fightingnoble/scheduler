# spec-writer

规范文档写作技能：将代码理解转化为结构化规范文档。

## 核心原则：设计思想 > 代码设计 > 具体实现

**问题**：技术文档常犯"细节堆砌"错误——把代码逐行翻译成文字，读者反而看不懂"为什么"。

**解决**：采用"总-分"结构，按信息价值递减排列：

```
价值递减 → 设计思想 → 代码设计思路 → 具体伪代码/代码节选
```

## 文档结构模板

```markdown
# [系统名称] 规范

**一句话核心**：[这个系统解决什么问题，用什么方法]

---

## 1. 设计思想 (20-25%)

### 1.1 关键设计决策（表格形式）

| 决策 | 问题 | 解决方案 |
|------|------|----------|
| 为什么用 X？ | ... | ... |
| 为什么 Y 而不是 Z？ | ... | ... |

### 1.2 核心设计原则（3-5 条要点）

---

## 2. 架构/流程 (30-35%)

### 2.1 整体流程图（ASCII art）

```
输入 → 处理阶段1 → 处理阶段2 → 输出
         ↓              ↓
       子系统A       子系统B
```

### 2.2 关键流程说明

---

## 3. 核心概念 (20-25%)

### 3.1 概念A（表格 + 一句话说明）
### 3.2 概念B（表格 + 一句话说明）
### 3.3 约定与注意事项

---

## 4. 接口速查 (15-20%)

### 4.1 API 列表（表格）

| API | 参数 | 返回 | 用途 |
|-----|------|------|------|

### 4.2 数据结构（简短代码块）

---

## 5. 实现细节 (10-15%，后置)

> 只有需要深入理解时才阅读本节

### 5.1 关键代码节选
### 5.2 性能特性
### 5.3 文件位置索引
```

## 写作检查清单

### 阶段 1：理解代码

- [ ] 阅读相关源文件，理解数据流
- [ ] 识别核心抽象和设计决策
- [ ] 画出数据流图（草稿）
- [ ] 列出关键 API 和调用关系

### 阶段 2：提取设计思想

- [ ] 回答"为什么用这个方案？"
- [ ] 回答"有什么替代方案？为什么不用？"
- [ ] 用表格对比设计决策
- [ ] 用一句话概括核心价值

### 阶段 3：组织文档

- [ ] 设计思想前置（Section 1-2）
- [ ] 接口速查居中（Section 3-4）
- [ ] 实现细节后置（Section 5+）
- [ ] 每节有明确小标题

### 阶段 4：精简与引用

- [ ] 删除重复内容
- [ ] 已有文档的内容用引用替代
- [ ] 代码节选不超过 20 行
- [ ] 表格优于长段落

## 常见问题

| 问题 | 表现 | 修正 |
|------|------|------|
| 细节堆砌 | 把 docstring 全贴进来 | 只保留方法签名和用途 |
| 结构混乱 | 想到哪写到哪 | 按模板组织 |
| 重复冗余 | 多处描述同一概念 | 单一来源 + 引用 |
| 缺少图表 | 纯文字描述流程 | 用 ASCII 图/表格 |

## 与现有文档的关系

参考 `doc/spec/readme.md` 中的文档层级：

```
key_COT.md (学术表达)
    ↓
e2e_sched_sim_flow.md (设计规范)
    ↓
test_plan.md (实现细节)
```

新文档应明确自己在层级中的位置，并与上层文档保持一致。
